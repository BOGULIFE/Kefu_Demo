# 静态Demo生成

## 输入与范围

- 阅读目标需求的需求单、PRD、UX设计需求表和最新修订，检查现有页面参考。业务规则不清楚时先澄清；已有授权的布局方案自行设计。
- 延续现有导航、信息密度、配色、表格和操作样式。右豹当前参考为暖白背景、橙色操作、深色文字和细边框；若用户提供更新参考，以最新参考为准。
- 沿用需求编号，仅实现本需求涉及的客户端和场景。当前阶段不自动接入交付中心或发布GitHub。

## 文件组织

在 `01-需求档案/{需求编号}-{需求简称}/04-静态Demo/` 维护：

- `{需求编号}-{需求简称}Demo.html`：必交的独立文件，内嵌所需样式、脚本及必要素材，可双击离线运行。
- 需要便于维护时保留 `index.html`、CSS、JS等源文件；修改源文件后同步重新生成独立HTML，避免两份行为不一致。
- 简短使用说明：入口、场景、演示数据、已模拟能力及限制。
- 页面预览放在同一需求的 `05-预览图/`；打包文件仅在用户要求或当前交付范围包含打包时放入根目录 `03-交付打包/`。

## 实现

1. 从UX需求表提炼主要任务和重要状态，建立场景清单后实现页面。静态Demo应能完成关键路径，不只是不可点击的视觉图片。
2. 使用本地模拟数据，不连接生产接口，不修改真实角色、组织或客服信息。模拟数据之间遵守PRD口径，必要时固定演示日期并在说明中注明。
3. 点击、选择、提交、返回、校验、分页等已展示操作给出可理解的结果；既有非本次功能可提示属于原有能力，不用无反馈按钮伪装实现。
4. 加载、全0/空数据、失败、无权限等状态按UX要求提供可复现的演示入口。将「原型演示」控件与业务操作区分，勿当作正式产品功能。
5. 若含导出，应提供符合约定格式的真实示例文件或明确的模拟反馈。不得把CSV改后缀冒充XLSX；文件与页面采用同一查询结果和范围，并标识演示数据。
6. 不依赖CDN、远程字体或仅能通过服务器运行的资源来支撑独立HTML核心能力。模块加载、fetch本地文件等可能妨碍双击打开时，改为内嵌或本地可用实现。

## 场景与嵌入约定

为后续交付中心提供稳定场景入口，例如 `Demo.html?scene=list`，场景编号使用本需求自己的清单：

- 直接打开某场景即可进入相应状态，刷新后仍可重现；未知场景回到合理默认页面。
- 支持 `embed=1`，只隐藏重复的外围框架，保留业务任务上下文与操作。独立打开保留完整页面。
- 如有H5和管理后台，分别提供可直接访问的场景URL，不靠截图代替其中一端。
- 嵌入模式不改变统计口径、权限模拟或主要交互逻辑。

## 验证与交付

- 本交付是用于产品评审的原型Demo。验证目标是业务流程呈现清晰、规则和结果正确，测试投入与原型用途相匹配。
- 使用可用浏览器走通核心业务链路，重点核对入口、关键操作、状态变化、角色权限和结果展示是否符合PRD；涉及两端时，用一个代表性案例串起两端流程。校验只检查影响业务规则的关键项，例如必填、指派对象和结果可见范围。
- 在实际涉及的后台和H5各选一个代表性视口，检查有无妨碍理解或操作的明显溢出、遮挡、弹层及导航问题，并保留主要页面预览。默认不开展像素级打磨、多尺寸或多浏览器矩阵、全字段组合、全部异常状态遍历、真实媒体兼容性及性能/压力测试；用户明确要求或已发现的问题需要时再针对性补充。
- 选择一种可用方式打开交付HTML验证核心流程；本地HTTP可作为浏览器无法打开独立文件时的替代。检查核心能力不依赖外网，不默认在离线、HTTP和嵌入模式反复跑同一流程；嵌入属于本次交付时，只补查入口和关键操作是否受影响。工具限制导致未验证的能力如实说明。
- 修复阻断业务演示、造成规则错误或明显误导的缺陷；核心链路通过且没有这类问题后结束验证。只有新增改动、失败或未解决问题才补做相关检查，不为验证而扩展测试范围。
- 交付独立HTML和预览路径，简述已走通的业务流程及模拟限制；默认不额外编写详尽UX测试报告或测试用例集。不要把文件生成或原型验证等同于生产功能上线。
