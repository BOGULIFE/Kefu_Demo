# 需求单

## 工作约定

- 本项目按「需求单 → PRD → UX设计需求表 → 静态Demo → 接入交付中心」推进。每次只完成用户当前要求的阶段；用户明确要求多个阶段时依其范围执行。
- 新需求编号必须询问用户，不自行递增或沿用 FR-wenkf-001。修改既有需求时沿用其编号。
- 项目根目录为包含 `portal` 与 `01-需求档案` 的目录。本项目当前为 `D:/软件数据/codex/在线客服-右豹`，移动后优先识别实际根目录。
- 阅读当前会话、用户提供的截图和已有需求文件。截图用于理解现状，不把截图中的全部功能自动纳入需求。用户最新明确的修订优先于旧稿；重要冲突先澄清。

## 收集与澄清

1. 提取原始诉求、要解决的问题、目标用户及预期结果，区分现有能力和本次变更。
2. 先查已有材料，再集中询问会影响范围、业务结果或权限的未知项。每轮优先询问少量关键问题，回答后只补问仍未解决的部分。
3. 统计需求特别核实：统计对象、归属关系、计数与去重、时间归日、转接/流转、历史起点、日期范围、状态快照或当前状态、空数据、导出范围。其他需求只问适用的问题。
4. 含糊表述如「总数」「经手」「处理中」「最近一年」需用具体场景确认，不用常识代替业务决定。
5. 会改变业务含义的疑点先请用户明确，再完成正式需求单。可先保存已知内容的草稿并明确标记；不把草稿冒充已确认版本。
6. 用户已授权自行设计的布局、分页、反馈等方案可自行确定，标明「方案设计」，不用重复请示。没有业务待定时写明「无」，不人为制造问题。

## 输出

保存到 `01-需求档案/{需求编号}-{需求简称}/01-需求单/需求单.md`。已存在则原位更新，不创建并行的“最终版2”。内容至少包括：

1. 基本信息：需求名、需求编号、产品、日期、当前阶段、涉及端口。
2. 需求背景：当前问题、现状限制、目标和本次价值。
3. 使用用户：分别列前端用户身份、管理端用户身份、其他端用户身份；未涉及的端明确写无新增，并描述权限与组织范围。
4. 关联页面入口：现有菜单、页面、具体操作位置，以及新增、保留或修改的部分。
5. 需求内容与业务口径：已确认能力、字段含义、适用条件和必要边界。
6. 用户使用路径流程：按角色和场景说明起点、关键操作、结果及返回路径。
7. 不允许出现的情况：列可判断的错误结果，如越权、数据混用、重复计数、旧结果覆盖等。
8. 这次不做的内容：记录明确排除项，防止后续阶段扩张。
9. 不明确/未定的内容：问题、影响、需谁确认；已解决的并入正文，不继续保留旧待定结论。
10. 后续阶段说明：只描述接下来可做什么，不自动产出后续文件。

## 完成检查

- 用户每项诉求都有对应条目，补充回答已合并，旧口径无残留冲突。
- 区分用户确认、现状事实与自行设计；不编造截图中看不到的信息。
- FR-wenkf-001 的会话、评价、工单和日期规则仅属于该需求，不作为新需求默认规则。
- 交付可点击的需求单路径，简述本阶段结果和仍待确认的关键问题。
